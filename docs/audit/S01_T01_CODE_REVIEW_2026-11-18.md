## Findings

### P2-1: `RequestContext` serializes any caller-supplied `act` / `policy_version` (RED)

`src/quati/application/identity.py:43-48`: `act: None = None` is only an annotation,
and the dataclass has no `__post_init__`. `to_wire()` is a bare
`json.loads(canonical_bytes(asdict(self)))`.

- `context(act=[{'actor_id':'root','principal_kind':'AGENT'}]).to_wire()`, a dict, a
  string and `[]` each emit that value as `act`. Contract section 3 says direct LOCAL
  contexts serialize `act: null`. The schema reserves a non-null chain for delegation,
  which T01 does not implement.
- `policy_version=''`, `7` and `['v']` serialize unchanged and fail the schema
  (`minLength 1`, `string|null`). The contract says non-null versions remain nonempty
  strings.

Tests: `test_direct_context_never_serializes_a_caller_supplied_delegation_chain`
(4 red) and `test_context_policy_version_is_null_or_a_nonempty_string_on_the_wire`
(3 red).

Risk: the only production constructor, `adapters/local_identity.py:193`, does not pass
either field, and `to_wire()` has no production caller yet. This is therefore a
defense-in-depth gap, not an exploitable path today. It becomes one when T02 or S02
starts serializing contexts, because forged identity-chain data would then ride an
object the existing test already treats as schema-complete. The existing
serializer test only covers `None` and `'trusted-policy'`, so it cannot catch this.

Suggested fix, not applied: validate in `__post_init__` or `to_wire` (`act is None`;
`policy_version` is `None` or a nonempty `str`).

### P3-1: `reduce_classification(proposed_capabilities=None)` raises a raw `TypeError` (RED)

`classification.py:140`. The input is trusted caller data, so this is not a bypass.
It is also not fail-closed or typed, unlike every other bad input in the module.
Test: `test_absent_proposed_capabilities_value_fails_closed_without_a_raw_crash`.
Suggested fix: normalize `None` to `()`, or raise a `Refusal`.

### Observations (no action required for acceptance)

- The first-turn conversation ID is generated on every `prepare`, so a discarded
  first turn burns an ID. The retried turn gets a new ID. Not a defect: nothing has
  been published. My test pins this.
- The receipt is written before `commit`. If `commit` refused after a successful sink
  (possible only when the single-owner/synchronous assumption is violated, for
  example re-entrancy inside the sink), a receipt would carry conversation metadata
  that the projection never adopted. The contract scopes concurrency to T03, so this
  is accepted by design. T03 must revisit it.
- `RequestContext.to_wire()` is exercised only by unit tests, not by any CLI path.
  The "direct RequestContext serialization" requirement therefore has L1 proof only.

## Conformity notes

- Typed classification: from_wire/to_wire preserve optional-field presence. `bool`
  is rejected for `confidence`, and 10^400, NaN, inf and 1.0000001 are rejected
  without overflow (new test, green).
- Reducer (M08-RT-01/RT-02): malformed registry effect values (`'READ'`, `None`,
  list, `True`, `0`, `''`, trailing space) and capability-id synonyms (case,
  whitespace, zero-width, NUL, bytes, int, None) all resolve to `dangerous`, route R2,
  `escalate`, `safe_work_allowed=False`. This holds even when the model claims a
  social/none/respond/safe proposal. An intent floor for `external_action` forces
  `ask`. In-place tampering of a loaded policy document is refused by the bound hash.
  All green.
- Conversation: a second `prepare` supersedes the first, and the stale candidate is
  refused with `CONVERSATION_PREPARE_MISMATCH` while the projection stays unchanged.
  Commit after `discard`, and an unusable ID generator, leave no state. All green.
- Receipt coordination through the real `CLIService._record`: a mid-session sink
  failure keeps the ID and revision 1, and the retry advances to 2 with the same ID.
  The caller's response object is not mutated. An owner mismatch never reaches the
  sink. All green.
