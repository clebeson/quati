# ADR-016 — Worker process model and the local inbox delivery sink

**Status:** Accepted (2026-11-15, owner authorization of implementation; specification v8.1). **Related:** ADR-013, ADR-015, RFC-003, RFC-013. **Audit:** A-01, A-05.

## Context
The product promise is proactive (reminders, updates by a recorded due time), but on a personal machine
nothing defines who runs the worker, what happens to timers while the machine sleeps, how the user learns
that reminders are not firing, or what "delivered" means before any channel adapter exists (S04).

## Alternatives considered
1. **Resident daemon installed and supervised by Quati.** Strong timeliness but needs per-OS service
   installers with privileges, which is intrusive for a personal tool. Rejected as the only model.
2. **Worker only while a CLI command runs.** Simple but nothing fires when no command is open; breaks
   the proactive promise silently. Rejected.
3. **Foreground loop plus drain-and-exit command usable from OS schedulers (chosen).** Works with systemd
   user timers, launchd and Windows Task Scheduler without privileges.
4. **Desktop notification as the first sink.** Not portable, no acknowledgement, can be disabled by the
   OS. Rejected as the system of record; kept as an optional best-effort extra.
5. **Pull-only `quati messages`.** No record of delivery. Rejected as the only mechanism.

## Decision
**Commands.** `quati worker run` is a foreground loop. `quati worker tick` drains all currently due work
and exits (exit code 0 when drained, a distinct code when work remains or a step failed). In the SERVER
profile the worker runs inside `quati server`; `worker run`/`tick` remain available for operations.

**Single instance.** At most one active worker per deployment, enforced by a lease row in the database
(`worker_locks`), renewed by the holder. A second worker exits with a lock error. An expired lease can be
taken over. In SERVER, additional instances are allowed only through per-work-item claims (ADR-015); the
deployment lock is a LOCAL rule.

**Heartbeat.** The worker writes a heartbeat row every `interval` (default 30 s, configurable).
`quati doctor` warns when the last heartbeat is older than 2x the interval, or absent while pending timers
exist, and says reminders are not firing.

**Timers and catch-up.** Each timer has `fire_at` and `fire_until` (the end of its usefulness window,
required). After sleep or downtime the worker fires each missed timer at most once: if now <= `fire_until`
it fires, with `late_by_seconds = now - fire_at` recorded in the timer, event and message; if now >
`fire_until` the timer becomes `EXPIRED`, nothing is delivered, and an audit event records it. Recurring
timers do not replay missed occurrences; they schedule the next future occurrence. Quiet hours and
interaction policy still apply to catch-up fires.

**Local inbox sink.** The first DeliveryPort sink is the `inbox_messages` table (`contracts/inbox-message.schema.json`).
- Committed to the inbox in the same transaction as the outbox transition means `DELIVERED`.
- The user reading it via `quati inbox` (alias `quati messages`) marks it `ACKNOWLEDGED`.
- An optional OS desktop notification is best-effort and never counts as delivery or acknowledgement; its
  failure never changes message state.
- The ERI timing oracle measures time to `DELIVERED`, not to a user read.

**Honest limit.** Timeliness holds only while a worker runs. Documentation, `quati doctor` and the
first-run message must say so.

## Consequences
- Users who want timely reminders run `quati worker install` (or `quati worker run`). `quati init`
  offers it but never installs services silently.
- Tick-based operation makes timer precision equal to the scheduler interval.
- Channel adapters (S04) add sinks later; the DELIVERED/ACKNOWLEDGED semantics of the inbox are unchanged.

## Platform scheduler notes (2026-11-15)
- systemd user timers with `Persistent=true` run a missed calendar trigger once after resume or
  boot; user timers cannot wake a suspended machine (`WakeSystem=` is not available to user units).
  This is why `fire_until` and the late-fire rule exist and why timeliness is promised only while the
  machine is awake.
- Equivalent catch-up behavior of launchd (`StartCalendarInterval`) and Windows Task Scheduler
  ("run task as soon as possible after a scheduled start is missed") is UNVERIFIED from primary
  sources and is an open verification item for S04 (WRK-02 on each OS).
- The normative scheduler settings written by `quati worker install` on each platform (missed-run,
  coalescing and overlap behaviour) are RFC-003 §12; where these notes differ, RFC-003 §12 applies.

## Amendment — `quati worker install|uninstall` (2026-11-15)
- `quati worker install [--interval 60s]` creates a **user-level** scheduler entry that runs
  `quati worker tick`: a systemd user service+timer with `Persistent=true` (Linux), a LaunchAgent
  (macOS), or a per-user Task Scheduler task (Windows). No root/admin, no resident daemon.
- Explicit only: it prints the exact unit/plist/task it will write and needs confirmation (or `--yes`).
  It is idempotent (re-running updates in place, records a digest of the written entry) and
  `uninstall` removes only entries it wrote. It refuses inside `QUATI_CAPABILITY_CONTEXT` (an agent
  cannot install persistence).
- `quati status` and `quati doctor` warn when due work exists and no heartbeat was seen within 2x the
  interval, and point to `quati worker install`.
- Verification: WRK-05 (local, with a fake scheduler backend); per-OS real install is
  `NOT_VERIFIED_EXTERNAL` until run on that OS.
