# ADR-015 — One LedgerPort with SQLite and PostgreSQL backends; ledger-driven worker instead of DBOS

**Status:** Accepted (2026-11-15, owner authorization of implementation; specification v8.1). **Supersedes:** ADR-003. **Related:** ADR-013, ADR-016, RFC-003, RFC-013. **Audit:** A-03, A-04, A-05.

## Context
Quati is local-first (Windows/macOS/Linux, no Docker, no database server for an individual) and must
also run for organizations (ADR-013). Quati already owns the business ledger: `commitment_events`,
`outbox`, `effect_intents`, `timer_intents`, leases and crash reconciliation. ADR-003 added DBOS on top
of that, which created two sources of truth (DBOS state and `workflow_refs`) and a reconciliation
problem that exists mostly because both are used. Mandatory PostgreSQL left the local profile without a
shippable database.

## Alternatives considered
1. **DBOS Transact (Python).** DBOS supports SQLite as its system database (configuration docs: "may be
   either Postgres or SQLite, though Postgres is recommended for production"), so a missing SQLite
   backend is NOT a reason to reject it. Its strongest argument would be a step checkpoint committed in
   the same transaction as application writes; whether that holds for SQLite, or only for PostgreSQL
   datasources, is not verified. DBOS version numbers and release dates are not verified and are not
   relied on here. Reasons it is still not chosen for v8.1:
   (a) it adds a second state model (workflow status, replay determinism) that must be reconciled with
   the kernel invariants and the versioned statechart;
   (b) the vendor itself labels SQLite as a development/test backend and recommends PostgreSQL for
   production, while SQLite is Quati's production backend for LOCAL. A multi-worker queue concurrency
   defect on SQLite was reported and has since been fixed; it is not a current limitation and is not
   a reason for this decision;
   (c) a checkpoint covers only database writes, not external effects, so the domain-specific parts
   remain Quati code in any case: `effect_intents`, outbox, `EFFECT_UNCERTAIN` reconciliation, timers
   with `fire_until` and the local inbox;
   (d) a separate system database would reintroduce two sources of truth and a crash window between two
   commits.
   What DBOS would replace is the claim/lease/retry loop. The hand-written scope is not small: the
   worker, leases, timers, recovery, lock and heartbeat are estimated at 1,500–2,500 lines of code
   plus two to three times as much test code (an estimate, not a measurement). The choice is a
   judgement call accepted with that cost. Rejected for v8.1; admissible later as a `DurableRunner`
   adapter (RFC-003 adapter admission).
2. **PostgreSQL job queues in the business database (Procrastinate, PGQueuer, pgmq, Absurd).**
   Procrastinate (in use since 2019) and PGQueuer show that a claim-plus-checkpoint design in the
   business database is established practice. Absurd describes itself as an experiment and is weak
   evidence. All are PostgreSQL-only and cannot serve LOCAL. The Quati worker follows the same
   pattern. Not adopted as a dependency.
3. **Temporal and other engine servers (Restate, Inngest).** The misfit is not "Docker required". Each
   adds a second resident process with its own store of truth. In addition, the Temporal local
   development server is documented as not intended for production use, Restate is not under an
   OSI-approved licence, and the default Inngest self-hosted mode keeps queue and state in memory.
   No history import exists. Rejected for v8.1 (Temporal removed from the `engine` enum).
4. **SQLite only.** Ideal locally, but no row-level security, weak concurrent multi-writer behavior and
   no network access for SERVER. Rejected.
5. **PostgreSQL only.** Contradicts local-first and A-03. Rejected.
6. **One LedgerPort, two backends and a ledger-driven worker (chosen).**

## Decision
1. **Persistence.** The application depends on one `LedgerPort`. Backends: SQLite (WAL mode on a fixed
   library version, otherwise rollback journal `TRUNCATE`; writes in `BEGIN IMMEDIATE`; foreign keys
   on; connection contract in RFC-003 §9) for LOCAL; PostgreSQL for SERVER with RLS (ADR-013) and the
   transaction contract of RFC-003 §10. Drivers:
   stdlib `sqlite3` and `psycopg` 3. DDL is portable: JSON stored as text (JSONB allowed on PostgreSQL
   through the adapter), timestamps as ISO-8601 UTC text on SQLite and `timestamptz` on PostgreSQL,
   mapped in the adapter. Every table has `tenant_id NOT NULL`; data objects have `space_id`; unique
   keys start with `tenant_id`. The uniqueness keys and expected-revision updates in
   BOUNDARY_CONTRACTS apply unchanged on both backends. The same DUR-* durability and crash tests run
   on both backends; a backend that cannot pass them cannot ship. The PostgreSQL backend is qualified
   only after the SQLite backend has passed its gate (RFC-003 §10).
2. **Migrations.** Plain numbered SQL files, one directory per dialect (`sqlite/`, `postgres/`), with a
   `schema_migrations` table recording version and SHA-256 checksum. A checksum mismatch stops startup.
   No ORM, no auto-generated migrations.
3. **Durable execution.** A ledger-driven worker. DBOS is NOT used in v8.1. `DurableRunner` stays as a
   narrow internal port (RFC-003) so DBOS or Temporal can be added later as adapters. The ledger is the
   only source of truth for execution state; `workflow_refs` is a ledger-owned view of work items, not a
   mirror of an engine.
4. **Worker loop.** Claim one ready work item with a lease; run one bounded step; in a single database
   transaction commit the event, outbox rows and the next timer; release or advance the lease. Every
   commit by a worker carries the lease epoch in its WHERE clause, so a worker whose lease expired
   cannot commit (fencing, RFC-003 §3). The step bound is enforced by client timeouts and a
   cooperative deadline check, not by killing threads (RFC-003 §4). On restart, expired leases are
   reclaimed. External effects follow the existing `effect_intent` and `EFFECT_UNCERTAIN` rules; the
   lease is never what prevents a duplicate effect. Exact semantics are in RFC-003.
5. **Stack picks (A-02/A-06/A-07).** CLI: Typer. Prompt assembly: pure Python, no Jinja2. Config: TOML
   read with `tomllib` from the `platformdirs` user config directory (SERVER: path from an environment
   variable). Secrets: `keyring` with environment-variable fallback, referenced only by `secret_ref`.
   Logs: JSON Lines, optional OpenTelemetry extra. Packaging: `uv tool install` or pipx. Lock: `uv lock`,
   cross-platform with hashes, runtime and test dependency groups separated. The lock requirement is a
   specification requirement; this ADR does not regenerate it.

## Consequences
- Quati owns lease, retry, timer and recovery code (estimated 1,500–2,500 lines plus two to three
  times as much test code). This is bounded and tested by DUR-* on both backends; no engine upgrade or
  licensing dependency exists. The DBOS system-database schema and the Procrastinate schema are used
  as review checklists for the claim and recovery code.
- SQLite allows one writer at a time; LOCAL throughput is limited accordingly, which is adequate for one
  principal. SERVER runs at `READ COMMITTED`, locks the commitment row with `SELECT ... FOR UPDATE` in
  every transaction that reads or changes that commitment, and uses `SELECT ... FOR UPDATE SKIP LOCKED`
  only for queue claims (RFC-003 §10).
- Engine history portability is no longer a concern in v8.1. Adding DBOS/Temporal later needs a new ADR,
  an adapter passing the DurableRunner conformance tests, and a drain plan for in-flight work.
- Enterprise HA for the worker (multiple SERVER instances) relies on lease claims and is verified only on
  PostgreSQL.

## SQLite operating constraints
The normative connection contract is RFC-003 §9; this section summarizes it.
- Journal mode by linked SQLite library version: WAL only on 3.51.3 or newer, or on the patched
  backports 3.50.7 or 3.44.6 (WAL-reset corruption bug in 3.7.0–3.51.2). On any other version the
  ledger runs with `journal_mode=TRUNCATE` (rollback journal) and WAL is never enabled. `quati doctor`
  reports the linked version, the active journal mode and the reason; the fallback is a WARN, not a
  refusal, and the ledger opens. Many stock Python builds link an affected version (CPython 3.14
  bundles 3.50.4), so a refusal would fail the first run on most machines.
- Connections: `synchronous=FULL`, `fullfsync=ON` on macOS, `foreign_keys=ON`, `busy_timeout` from
  `ledger.sqlite_busy_timeout_ms`; Python `sqlite3` opened with `autocommit=True` and every write
  transaction started with an explicit `BEGIN IMMEDIATE`; schema migrations run inside
  `BEGIN IMMEDIATE`.
- The LOCAL ledger file must be on a local filesystem. `quati doctor` and startup refuse network
  filesystems and synced folders (for example OneDrive, Dropbox, iCloud Drive, Google Drive) in both
  journal modes: file locking is unreliable there, a sync client can replace or separate the database
  and its journal files, and WAL needs shared memory on one host. Detection is best-effort.
- One writer at a time; writes use `BEGIN IMMEDIATE` with a bounded `busy_timeout`.
- Backup uses `VACUUM INTO` or the SQLite online backup API, never a file copy of a live database;
  restore marks every non-terminal effect intent `EFFECT_UNCERTAIN` (RFC-003 §11, M28).

## Verification
DUR-01..04 on both backends; migration checksum tampering test; lease reclaim after a killed worker;
claim exclusivity under two concurrent workers on each backend; a two-connection concurrent write
stress test in the journal mode selected by the version gate (with checkpoints in WAL mode) and a
sleep/resume lease test on SQLite in which the original holder's late commit is rejected by the
lease-epoch check (DUR-09, DUR-10).

**ACCEPTANCE_CASES.md** — add:
- `DUR-06` two workers contend for one work item on each backend: exactly one claims; the other gets none.
- `DUR-07` kill the worker mid-step: after lease expiry another worker reclaims and the event/outbox/timer commit is exactly once.
- `DUR-08` migration file edited after being applied: startup fails with a checksum error on both dialects.
- `WRK-01` second `quati worker run` for the same deployment exits with a lock error while the first holds the lease; takes over after expiry.
- `WRK-02` timer due while the machine was off, `fire_until` not passed: fires once with `late_by_seconds` set.
- `WRK-03` timer whose `fire_until` passed: becomes `EXPIRED`, no message is delivered, an audit event is recorded.
- `WRK-04` no heartbeat within 2x interval: `quati doctor` reports a warning and exit code per the CLI contract.
- `DEL-L01` inbox commit marks DELIVERED; `quati inbox` read marks ACKNOWLEDGED; a desktop notification failure or success never changes state.
- `DEL-L02` inbox rows of another tenant or space are never returned (RLS on SERVER, query scope on LOCAL).
